# 運用設計

## 現在の状態

AWSスタック・CLI・運用環境は未作成。この文書は実装時に満たす運用要件であり、実行可能なrunbookではない。
デプロイコマンド、復旧コマンド、監視閾値は実装・検証後に追記する。

## 定期実行

EventBridge Schedulerが単一Lambdaを起動し、Git管理した設定に基づいてRSS / Atomを収集する。
周期、タイムゾーン、再試行上限、DLQの採否、最大実行時間をIaC実装時に確定する。
SchedulerやLambdaの再試行に同じ論理run_idを渡せるようにする。
重複配信、実行時間超過、前の実行との重なりを前提にする。

## 部分失敗

フィード取得・解析失敗はsource_idと原因を記録し、他の情報源を継続する。
Raw保存に失敗した入力を、保存・再処理可能な成功として扱わない。
実行結果では成功・部分成功・全件失敗を区別し、保存されたmanifestで追跡できるようにする。
保存基盤の障害などmanifestも書けない場合は、ログとLambdaの失敗で把握する。

## 再実行・復旧

同一実行の再試行と、新しい時刻での収集を区別する。
replayは元のRaw・取得メタデータを使い、設定と正規化のバージョンを追跡する。
途中まで保存された未完了バッチは取り込み側から見えないようにする。
索引更新・manifest公開の中断復旧と、失敗した情報源だけの再試行方法を実装前に決める。

## 観測

run_id、source_id、stage、成功・失敗数、Document新規・更新・重複数、Discovery数、実行時間を記録する。
ログに秘密情報を含めない。URLに秘密が含まれ得るため、情報源IDをログの基本キーにする。
CloudWatch Logsの保持期間、全件失敗の通知方法、部分失敗の検知方法、S3リクエスト数を確認する。
製品機能としての通知はv1対象外だが、運用上の障害検知は設計対象とする。

## 保存・権限・費用

バケットは非公開とし、開発時に収集データを誤削除しない保持方針を決める。
Rawのライフサイクルは再処理可能期間に直結するため、初期値を勝手に短くしない。
IAMは対象prefixへのGetObject / PutObjectと、必要な範囲のListBucketなど実装で使う操作に限定する。
HeadObjectにはs3:GetObjectが必要。秘密情報を使わないRSS収集に不要なSecrets Manager権限を付けない。

S3索引の読み書き量と小さなオブジェクト数、Lambda実行時間、ログ量を評価する。
自宅サーバへの常時接続やAWSからのPushは不要。将来は自宅側からS3をPullする。
